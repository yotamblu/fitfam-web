# FitFam

FitFam is a gamified hybrid-training (strength + endurance) PWA, built as a Next.js app, tied to an Instagram/TikTok fitness community. Points, streaks, leaderboards, and a Duolingo-style winding training roadmap are core, not decorative — they're the primary retention mechanic.

**Visual identity:** dark, dense, "athletic control-room" aesthetic — near-black surfaces, hairline borders instead of drop shadows, tabular numerals for live data, and a two-accent system (a hot ember/orange for action and streaks, a lime "volt" for completion/success) laid over a mostly-Hebrew RTL interface with embedded LTR numeric clusters (weights, times, BPM).

The design system was reverse-engineered from a Google Stitch export (`/design-reference/`), not designed from scratch. It contained three competing color-palette directions; this is now resolved: **"Legacy" is the canonical palette for the whole app**, with one confirmed exception — **the Training Roadmap screen uses its own "Obsidian Kinetic" skin** (true-black background, sharper ember/volt accents), since the user continued refining that specific screen in Stitch after the rest of the app was drafted. See [`docs/design-system/inconsistencies.md`](docs/design-system/inconsistencies.md) #1 and `tokens.md §1.5`.

## Rules of thumb

- **Never hardcode a hex value, font size, spacing value, or radius in a component** — pull it from `docs/design-system/tokens.md` / the Tailwind theme it maps to.
- **Check `components.md` before creating a new component** — most workout/leaderboard/gamification UI already has a named counterpart there; extend it rather than duplicating.
- **Use the Legacy palette everywhere except the Training Roadmap screen**, which uses its own confirmed "Obsidian Kinetic" tokens (`tokens.md §1.5`) — don't let that screen's colors leak elsewhere, and don't build the Roadmap screen from `training_roadmap_path_1`/`path_2` (superseded); build it from `training_roadmap_path_3`.
- **Preserve the RTL/bilingual convention**: Hebrew content flows `dir="rtl"`, but numeric/Western data clusters (weights, times, BPM, dates) are wrapped `dir="ltr"` inline — see `tokens.md §2.4`.
- **The export is mobile-only** — there is no verified tablet/desktop layout; treat any responsive behavior as new design work, not extraction.
- Placeholder image URLs (`lh3.googleusercontent.com/...`) in the original export are Stitch scratch assets — never ship them; replace with real or self-hosted media.
- **Top-edge rule (iOS PWA status bar) — applies to every page, always.** iOS paints the status-bar strip as ONE flat colour, taken from the fixed `components/StatusBarTint.tsx` element (colour token `--color-status-tint`, `app/globals.css`). It cannot show a grid, glow, image or gradient. So **never let any page content, background, grid, glow, image or card start with a hard edge at the top of the page.** Fade it in from the tint colour (see the `h-24 bg-gradient-to-b from-status-tint via-status-tint/60 to-transparent` overlay in `app/page.tsx`) — or do whatever else it takes so the page meets the strip with no visible line. On a new page whose top colour differs, keep the strip and the fade matching (update/override the tint) rather than leaving a seam. Keep `StatusBarTint` mounted in `app/layout.tsx`, and keep `viewport-fit=cover` plus the `apple-mobile-web-app-*` meta tags.
- **Landing map copy:** the stops are workouts ("אימון 01" …), and the last stop is the level-ending challenge, labelled "אתגר מעבר רמה" (`challenge: true` in `components/hero/weeks.ts`). Copy elsewhere (`app/page.tsx`) may still say "שבוע".
- **Animations: animate only `transform`, `opacity` and cheap `clip-path`** — never SVG `mask`, `mask-image` over animated content, or per-frame filter/blur changes (janky on iOS Safari). Keep loops in CSS, not React state.
- **Auth (Google only):** the login buttons in `components/AuthActions.tsx` are styled `aria-hidden` visuals with Google's real button laid invisibly on top (`components/GoogleButtonOverlay.tsx`), because Google returns an ID token only through its own button. The token goes to the API through a same-origin proxy: the browser calls `/backend/*` (`lib/api.ts`) and the route handler `app/backend/[...path]/route.ts` re-sends it server-side to `API_ORIGIN` (server-side only; defaults to `http://localhost:8081` in development and is REQUIRED in production, where the route answers 503 `api_not_configured` without it; `maxDuration` is 60 s so a sleeping free-tier API can wake up; path segments containing `..`, slashes or null bytes are rejected). It is a route handler, not a `rewrites` entry, because browsers add an `Origin` header to POSTs and the API's CORS allowlist rejects a tunnel/phone origin (403 "Invalid CORS request"; the UI shows the generic error), and a rewrite cannot drop that header. The proxy only forwards `auth/*` (extend `ALLOWED_PREFIXES` as features need), rejects requests whose `Origin` is not this site, and forwards only content-type/accept/cookie and Set-Cookie. This keeps the login cookie first-party, which iOS Safari requires, and only the web app needs a tunnel for phone testing (`cloudflared tunnel --url http://localhost:3000`); the API needs none. The session is an HttpOnly cookie, never in localStorage. Env (gitignored `.env.local`): `NEXT_PUBLIC_GOOGLE_CLIENT_ID`; optional `NEXT_PUBLIC_API_URL` to bypass the proxy (leave unset in production). On Vercel set `API_ORIGIN` + `NEXT_PUBLIC_GOOGLE_CLIENT_ID`, pick the function region next to the API, and add the site's https address to Google's Authorized JavaScript origins. Only emails already added by an admin can log in; after login `AuthActions` sends the customer to `/home` (an already signed-in visitor sees a button to continue).
- **Signed-in app (built 2026-10-12, not pushed):** route group `app/(app)` (the session gate `components/app/Session.tsx` loads user,
  plans and stats once; no session -> back to `/`), tab screens in `app/(app)/(tabs)` (`/home`, `/roadmap`, `/profile`; `template.tsx`
  plays an entrance animation on every navigation) and stack screens `/workout/[id]` and `/workout/[id]/play` (the optional guided player:
  rest ring timer, wake lock, progress saved per step). Responsive: below `lg` a header + bottom tab bar, from `lg` a fixed side bar
  (`TabShell`) and two-column pages; stack pages scale from `max-w-2xl` to `max-w-5xl`. The roadmap (`RoadmapMap.tsx`) is ONE tall SVG
  (fixed viewBox width, scales with its container) with a Catmull-Rom path through every stop drawn as a striped candy-style road, the walked part lit in the level colour and drawn
  by a clip rect animated with `transform`; every level is a zone painted as a top-down training venue (`RoadmapScenery.tsx`: `dominantVenue` picks the venue from the sport most of the level's workouts are tagged with: running track / swimming pool / gym floor / outdoor calisthenics park (so a mixed plan can change venue level by level just by how its workouts are tagged); the level picks the time of day:
  day, sunset, night; scenery generated in code, no image files; the road, ribbon banner and stop colours follow the venue and level). Each level challenge sits on the BORDER between two zones (a chequered gate line across the road, `gates` in `RoadmapMap.layout`) and the next level banner is just below it; stops and level banners are HTML placed by percentage on top of it, sized with container
  units (`cqw`); levels flow one after another (no folding); it scrolls to the current stop and shows a "back to my spot" button. The game
  layer (points, account level + Hebrew rank titles in `lib/gamify.ts`, weekly streak, 6-week chart) comes from the API `GET /me/stats`.
  Motion: CSS classes `ff-*` at the end of `globals.css` (transform/opacity only; reduced-motion switches them off), `Reveal`, `CountUp`,
  `ProgressRing`, `Confetti`, `Skeleton` and `BrandLoader` in `components/app/ui.tsx`; every data load shows a skeleton or the branded loader,
  never a blank page. The launch splash (root layout) plays for signed-in visitors too: `RedirectIfSignedIn` on `/` just redirects to `/home` under the splash. The proxy allowlist now includes `auth/`, `me/`, `workouts/`, `challenges/`. Verified in a real browser at desktop and
  phone width with a throwaway customer (removed afterwards); NOT verified on iOS / as PWA, and the customer web build was not run (tsc + lint pass).
- **Look and feel rules for the signed-in app (researched 2026-10-12, five rounds, so it does not look AI-generated; keep following them):** one primary action per screen and a size hierarchy (one big number or title, everything else quiet); tonal surfaces (`Card` / `RowList` in `components/app/primitives.tsx`), no border or glow on cards, hairline dividers inside a grouped surface instead of boxes in boxes; one radius for cards (16px), one for controls (12px, pills only for the roadmap game buttons); no glow orbs, no blur blobs, no glass panels, no gradient text, no emoji as icons; icons are outline, filled only to mark an active state; the accent colours keep one job each (ember = action and the current thing, volt = done and points); type weights 500/600/700 only (Heebo 800 is loaded but avoid it), numbers tabular; motion is ease-out, 150-400 ms, no bounce or overshoot, nothing above 600 ms, transform/opacity only, and every animation must communicate something (the one continuous cue is the current stop on the roadmap); loading is a calm pulse on blocks that hint at the layout (`Skeleton`), never a blank screen; copy is short and factual, no exclamation marks outside real milestones; touch targets at least 40px (primary controls 48px); one visible focus ring. The research sources are summarised in the 2026-10-12 conversation, not stored here.
- **Dynamic app bars (built 2026-10-12):** the sticky header, the desktop side bar, the bottom bar and the iOS status strip (`StatusBarTint`, reads CSS var `--chrome-tint`; also the `theme-color` meta) wear the colour of the current venue and level (`Theme.chrome` / `accent` in `RoadmapScenery.tsx`). Default everywhere = the classic orange (`DEFAULT_TINT` in `Chrome.tsx`), static, no plan colours and no plan switcher outside the roadmap (the user asked for this); only on `/roadmap` the map reports (`useChromeOverride`, `Chrome.tsx`) the zone under the top of the screen, the bottom of the screen and the middle, so the bars change colour as you scroll through levels. Glows on the calm pages are static (the user did not like pulsing light on Home/Profile). The roadmap page is in its own "game" design language: `RoadmapHud` (chunky plan buttons only: the one place plans are switched) sits in the header on phones and sticks above the map on desktop, the whole page background is tinted with the zone colour, the desktop summary is a glossy panel, `Button variant="game"` is the chunky candy button. Stack pages (workout, player) keep the default colours.
- **Page gutter:** `--spacing-gutter` (16px) is defined in `app/globals.css`; `px-gutter` / `-mx-gutter` depend on it (it was missing once, so content touched the screen edges on a phone).
- **Keep this file and `../CLAUDE.md` current:** whenever you work here, check whether they are out of date (features built, commands, conventions) and update them yourself, without asking.
